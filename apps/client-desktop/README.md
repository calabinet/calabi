# calabi-desktop (M7-S6)

A thin Tauri 2 shell that wraps the calabi daemon's local SPA
(`http://127.0.0.1:7400`) in a native window with a system tray and
auto-update channel.

The daemon binary (`calabi`) is shipped alongside this app: the desktop
binary is responsible for starting/stopping the daemon process, watching
its `/healthz`, and rendering the same browser UI Mac/Windows/Linux
users would see at `http://127.0.0.1:7400` in their browser. No
separate frontend project — the WebView loads the daemon's embedded
SPA directly.

## Layout

```
apps/client-desktop/
├── README.md
├── icons/                 # Generated by `cargo tauri icon`
├── shell/index.html       # Loading / redirect fallback
└── src-tauri/
    ├── Cargo.toml
    ├── build.rs
    ├── tauri.conf.json
    └── src/
        ├── main.rs        # Window, tray, daemon supervisor, updater
        └── daemon.rs      # Spawn / monitor the calabi binary
```

## Local build

Prerequisites:
- Rust 1.75+ (`rustup install stable`)
- Node 18+ (only for `cargo tauri` CLI install via npm; not for the app)
- On Linux: `webkit2gtk-4.1-dev`, `libssl-dev`, `libgtk-3-dev`,
  `librsvg2-dev`, `libayatana-appindicator3-dev`
- On macOS: Xcode CLI tools
- On Windows: MSVC build tools + WebView2 runtime (preinstalled on Win11)

```sh
cargo install create-tauri-app tauri-cli
cd apps/client-desktop/src-tauri
cargo tauri build      # produces installers under target/release/bundle/
```

For day-to-day dev:

```sh
cd apps/client-desktop/src-tauri
cargo tauri dev        # opens the window pointed at http://127.0.0.1:7400
```

(Make sure `calabi daemon` is running in another terminal first, or rely
on the in-app supervisor to start it.)

## Daemon supervisor

`src/daemon.rs` finds the `calabi` binary by:

1. `$CALABI_DAEMON_PATH` env var — **debug builds only** (see below)
2. The daemon **embedded in this exe**, extracted to app-local-data
   (production: the self-contained single-exe path)
3. Sibling `calabi(.exe)` next to the desktop binary
4. `which calabi` / `where calabi` on PATH

> **Why the env override is debug-only.** A shipped, signed
> `calabi-desktop.exe` must never let an environment variable decide which
> executable it launches. It is also a footgun: a dev box with a *permanent*
> User-scope `CALABI_DAEMON_PATH` silently ran its repo build instead of the
> daemon baked into the downloaded release — every process launched from
> Explorer inherits User-scope vars, including production installs. So keep the
> override **session-scoped** (`$env:...`, current shell only), never
> `[Environment]::SetEnvironmentVariable(..., 'User')`.

If none found, the tray shows "daemon binary missing" and prompts the
user to download it. After starting, the supervisor polls `/healthz`
and updates the tray icon variant (green / amber / red).

### Daemon binary location (single source of truth)

There is ONE canonical path for the daemon binary in this repo:

```
bin/calabi(.exe)         # at the repo root, matching Makefile BIN_DIR
```

Every doc, every runbook, every `make build`, and `scripts/build-desktop.{ps1,sh}`
write here. Do not check in or hand-create other copies under
`apps/client/bin/`, `apps/client-desktop/`, or
`src-tauri/target/release/` — those used to exist as legacy outputs
and caused "which version am I running?" confusion. The build script
copies `bin/calabi(.exe)` into `src-tauri/target/release/` (the
sibling-fallback location) as part of `scripts/build-desktop.{ps1,sh}`;
that copy is regenerated every build, never edited by hand.

### Daemon bundling (self-contained exe)

The daemon is baked INTO the desktop exe — the shipped
`calabi-desktop.exe` is self-contained, with no sidecar file and no
separate install. `src-tauri/build.rs` reads the binary staged at
`src-tauri/binaries/calabi(.exe)` (put there by
`scripts/build-desktop.{ps1,sh}`) and `include_bytes!`s it. At runtime it
is extracted to app-local-data under a filename derived from a build-time
content signature (`CALABI_DAEMON_SIG`), so each desktop release extracts
its own daemon instead of reusing a stale cached copy.

Always build releases with `scripts/build-desktop.{ps1,sh}`. A plain
`cargo tauri build` on a fresh checkout stages nothing, emits a
`cargo:warning`, and yields an exe with an empty payload that falls back to
a sibling/PATH calabi at runtime.

* **Dev (recommended)**: point `CALABI_DAEMON_PATH` at the canonical bin —
  **for the current shell only**:
  ```powershell
  $env:CALABI_DAEMON_PATH = "$PWD\bin\calabi.exe"  # from repo root
  ```
  before launching `cargo tauri dev`. Re-run `make client` (or
  `go build -o bin/calabi.exe ./apps/client/cmd/calabi`) and the next
  daemon restart picks up the new binary -- no copying needed. Release
  builds compile this override out, so it can never leak into a shipped app.
* **Manual install (rare)**: copy `bin\calabi.exe` next to
  `calabi-desktop.exe` to exercise the sibling fallback.
  `scripts/build-desktop.ps1` already does this copy into
  `src-tauri/target/release/` as part of the build.

## Auto-update

We use Tauri's built-in updater. The release flow lives in
`docs/runbook/m7-desktop.md` — short version:

1. Tag a release in git: `desktop-vX.Y.Z`
2. CI builds the bundles + signs with the team's private update key
3. Uploads `latest.json` + per-platform binaries to GitHub Releases
4. Existing installs check `latest.json` on launch + every 6h

The signing key fingerprint is committed in `tauri.conf.json` under
`plugins.updater.pubkey`. The private half is held in 1Password.

## Code-signing

- **Windows**: EV code-signing cert from DigiCert (annual ~$400). Build
  step uses `signtool.exe` (configured via `tauri.conf.json`).
- **macOS**: Apple Developer ID Application certificate. Notarization
  via `xcrun notarytool`. Both require Apple Developer membership ($99/y).
- **Linux**: no signing required for AppImage; .deb signed with a
  detached GPG signature.

See `docs/runbook/m7-desktop.md` for the full release checklist.
